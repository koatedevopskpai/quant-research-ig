Independent checks of the statistical claims:

- **Published example reproduced.** `expected_maximum_sharpe(0.002, 100)` =
  0.1132 and `probability_from_moments(2.5/√250, ·, 1250, −3, 10)` = 0.9004;
  0.9505 with 46 trials. These match the worked example in Bailey & López de
  Prado (2014, pp. 9–10), so the implementation is anchored to an external
  reference rather than to its own output.
- **Zero-skill calibration.** 1000 independent random walks (n = 252,
  σ = 0.01), true Sharpe = 0:

  | Formula | Flagged significant (PSR ≥ 0.95) |
  |---|---|
  | pre-repair (annualised SR in a per-period variance term, excess kurtosis) | **47.5%** |
  | phase-2 implementation | **5.9%** |

  A 47.5% false-positive rate is the reason the earlier "every strategy is
  gated" claim could not stand: the gate would have admitted half of all
  random series.
- **Folds fit models.** `check_validation.py` reports 15 CPCV model fits and 3
  chronological WFA fits; the tests assert training/test index separation,
  embargo distance, fold-local scaling, and invariance to edits in the outer
  holdout.

## Defect found during review (fixed)

**Fresh-clone `tmp_path` failure.** Phase 1 sets
`--basetemp=test-results/tmp` in `addopts` while `.gitignore` excludes
`test-results/`. Nothing created the directory, so on a clean checkout every
`tmp_path` fixture errored at setup:

```
FileNotFoundError: [WinError 3] .../test-results/tmp
```

The delivered run passed because an earlier `--junitxml=test-results/junit.xml`
run had already created the folder — the exact "works on my machine" class of
failure the baseline phase exists to remove. Fixed in `conftest.py`
(`pytest_configure` creates the parent). Reproduced before the fix
(471 passed, 24 skipped, 1 error), green after (472, 24, 0).

## C++ extension (not in the phase scope)

Phase 1 deliberately leaves the accelerator unbuilt, so all 24 C++ tests skip.
That makes the module at the centre of the project's `hft-engine` claim
unexercised on a fresh clone. Added, in separate commits:

- `hft-engine/cpp/build_cpp.{sh,ps1,bat}` — portable, venv-aware build
  (`PYBIND11_FINDPYTHON=ON` so the module is compiled for the active
  interpreter, not the system one — the previous CMake setup silently built a
  wheel for the wrong Python).
- CI job that builds the extension on Ubuntu and fails if any `hft-engine` test
  skips.
- After building: 150/150 `hft-engine` tests pass, including all 24 C++ tests.

Benchmark, CPython 3.12.15, 100 levels, 4000 calls, median (each C++ figure
includes the pybind11 boundary):

| operation | Python (µs) | C++ (µs) | ratio |
|---|---:|---:|---:|
| `apply_diff` | 2.90 | 0.90 | 3.2× faster |
| `l1_snapshot` | 1.40 | 2.70 | 0.5× (slower) |
| `depth_summary` | 8.00 | 2.40 | 3.3× faster |

`l1_snapshot` is slower through C++. That is the honest boundary result: a
single scalar read does not repay a pybind11 call. Raw JSON:
`evidence/bench-order-book.json`.

## Still outstanding (phases 3+)

Reproduced by the 2026-10 review and **not** fixed by phases 1–2; listed in the
README's Known Limitations so nothing here overclaims:

1. Lightstreamer callback name (`on_item_update` vs SDK `onItemUpdate`), field
   enumeration via `getValue`, and `LTP`/`Ltv` key casing.
2. L1 top-of-book quotes applied as L2 incremental depth, retaining stale
   levels; live L1 has no sizes.
3. One book/analyser/price cache for all EPICs in the runner; no per-instrument
   isolation.
4. Execution accounting: no order IDs or lifecycle, holdings updated on order
   creation, position limits computed from absolute holdings so exits are
   blocked.
5. Risk: `risk.kill` recursion and `resume()` republishing the kill topic; P&L
   from price level rather than mark-to-market holdings.
6. API binds `0.0.0.0` with unauthenticated mutation endpoints and permissive
   CORS.
7. Ingestion fills open from close; timezone-naive timestamps not normalised.

CI has not run remotely; no Linux or PostgreSQL result is claimed here.
